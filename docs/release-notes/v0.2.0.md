# Oddsmaker v0.2.0 Release Notes

> Scope: the P7 competitive gap convergence batch (analytics capabilities visible in the console added since v0.1.0). See the P7 section of `todo.md` for the overview, and `docs/competitive-analysis.md` for the planning basis.

## Highlights

### Real-Time Event Inspector (P7-1, Live Inspector)
- Integration troubleshooting: a Gateway in-memory ring buffer records the outcome of every event (accepted / rejected / sampled_out / duplicate), including rejection reasons and schema validation details.
- Inspector API: Gateway `GET /v1/inspector/recent?game_id=&environment=&limit=&outcome=` (filtered by API Key scope); control-plane proxy `GET /api/inspector/{gameId}/recent`.
- A new Live Inspector page in the console (polling refresh) shows "did the event arrive, and why was it rejected" on one screen.

### Reusable User Segments (P7-2, Segments)
- Segment definitions: combinations of attribute + behavior conditions (up to 20 conditions per segment), supporting computation, member preview, enable/disable, and soft delete; members are materialized to ClickHouse `segment_members` (ReplacingMergeTree).
- Segment filter injection into reports: all six report families — online / retention / payment funnel / finance / Crash / risk — plus dashboards support the `segment_id` parameter, and each console report page provides an "all segments" dropdown.
- Segment retention via pre-aggregation: `retention_daily` gains a `subject_id` subject dimension (player>user>device, aligned with the segment materialization key); member filtering is pushed down to ClickHouse; when the pre-aggregation has no historical data, it automatically falls back to real-time computation over events (window clamped to 90 days + 15s query timeout protection).
- Permissions: read `segment:read`, write `segment:manage` (DB migration V0.9.12).

### Widget-Based Custom Dashboards (P7-3, Dashboards)
- Dashboard CRUD saved per game, with layout JSON validation (widget type/data source allowlists, numeric clamping of params, span normalization to a 12-column grid).
- Console widget editor: KPI / line / bar / table × online / retention / payment funnel / Crash — four data sources freely combinable.
- Permissions: read `dashboard:read`, write `dashboard:manage` (DB migration V0.9.13).

### Full Raw Data Export (P7-4, Raw Export)
- `events` exported as JSONL by daily partition (gzip optional) to an export directory, with batched cursor-based reads (upper limit of 5 million rows per partition).
- The manifest records row count/bytes/SHA-256 and is written atomically; partition list API `GET/POST /api/games/{gameId}/events-export` + a console export page; object storage is synced from the export directory on the ops side.
- Async generation + expiry cleanup + full audit; reuses the `export:execute` permission.

### Risk Sequence Rules (PATTERN)
- The final piece of the risk rule types: ordered event sequence detection (e.g. login→purchase→refund completed within a short time → suspected fraud/scripts). With this, all seven risk-job rule types (THRESHOLD / FREQUENCY / VELOCITY / RATIO / DUPLICATE_RECEIPT / AD_REWARD / PATTERN) are fully live.
- Rules are configured on the control plane via the `ruleConditions` JSON to define the sequence (`"sequence": [event names...]`, 2-8 steps) and the `timeWindowMinutes` window, validated on both create and update; RuleFetcher delivers to risk-job within 60s, no restart needed.
- Detection is a keyed state machine (KeyedProcessFunction + ValueState): the window starts from the first step, expired windows are lazily invalidated, a repeated first step automatically restarts, and matching resets so it can match again; no flink-cep dependency introduced, and state carries a 1-day TTL as a reclamation fallback.

### Dimension Sync Agent (oddsmaker-agent) and sync-status API
- The open-source dimension sync agent has landed: `agents/dimension-sync-agent/` (a standalone Gradle module with zero in-repo dependencies, deployable directly into a game studio's intranet). It supports two source families: MySQL/PostgreSQL incremental queries (single ? placeholder + ORDER BY watermark column, watermark rebinding recovered by type tag) and CSV directories (RFC 4180, file-granularity checkpointing); local checkpoints are atomically persisted and advance only after a successful push, with automatic replay on failure (downstream ReplacingMergeTree is idempotent).
- Sync observability: the agent reports a heartbeat to Control every round via `POST /api/dimensions/sync-status`, adding the V0.9.14 `dimension_sync_status` table and the `dimension:read` / `dimension:manage` permissions; `GET /api/dimensions/sync-status?gameId=` returns each source's position, cumulative push/error counts, and two notions of lag (`sinceLastPushSeconds` = agent liveness, `sinceLastEventSeconds` = source freshness).
- Source expansion and observability surface: the agent adds an `excel` source (standard-library zip+xml minimal xlsx parsing, no POI; shared/inline strings, `r` column reference positioning, restoration of large numbers in E notation; formula recalculation and date formatting unsupported — date columns should be exported as epoch millis or ISO text) and a `kafka` source (message body = a JSON object, control-column semantics as above; offsets self-managed via checkpoint `k:0=42;1=57`, not depending on broker group offsets; bad messages are skipped but the offset advances to prevent poison-pill deadlock — verified end-to-end against apache/kafka:3.7.0 single-node KRaft: all five scenarios green — earliest startup / checkpoint-seek resume (checkpoint takes priority over group offset) / mid-run partition expansion catch-up / poison-pill skip with offset advancement / drain capped at 100 rounds of bounded resume — and a checkpoint bookkeeping defect found and fixed in testing (partitions with no new data in a round used to lose their cursor entry, causing the entire segment to be replayed next round)); the console gains a dimension sync management page (web `/dimensions`, heartbeat health tiers + two lag notions + recent errors, 5s polling that can be turned off, `dimension:read` read-only).

### Python Training Pipeline (P4.4, oddsmaker-ml)
- Trainable models landed: `ml/` (the `oddsmaker-ml` Python package, numpy/pandas/scikit-learn) supplies a training pipeline for P6's heuristics — churn (label = no events within 14 days after the snapshot, LR), pltv (D7→D30 multiplier through-origin WLS, w = cohort size), risk (label = escalated block/review dispositions from risk_actions, class_weight=balanced LR), propensity (payment propensity, label = a payment event within 14 days after the snapshot, feature definitions identical to churn, LR + the `PropensityScorer` heuristic baseline, mirrored on the Java side with the same formula as fallback).
- Interpretability first: all linear models, outputs are versioned JSON (`feature_names + coefficients + intercept`, schema_version=1); the Java side scores via dot product + sigmoid, with no Python runtime required; every artifact carries its own heuristic baseline comparison (`auc_gain_vs_heuristic` / held-out cohort MAPE), so the model's gain over the heuristic is auditable.
- One-command run-through: `python3 -m oddsmaker_ml train --model all --source synthetic` runs the full offline pipeline on seeded synthetic data (data→features→training→evaluation→artifact export) with fully reproducible results; the ClickHouse HTTP real-data entry point depends only on the standard library urllib (JSONEachRow).
- Write-back path (Control side): `POST /api/ml-artifacts` registers versioned artifacts (validation semantics aligned with Python `validate_artifact`, retraining on the same version overwrites, writes audit; `ml:read / ml:manage` permissions, V0.9.15 `ml_model_artifacts` table), and `refreshChurn / refreshRiskScore / refreshPltv / refreshPropensity` batch-score by feature_names against ClickHouse features and write back to `predictions` (TTL 30 days as before); the propensity leaderboard API is provided in step (`GET/POST /api/prediction-metrics/{gameId}/propensity[/refresh]`). When an artifact is present and passes validation, the model score is preferred (`path=model`); when missing/corrupted/feature-definition mismatched, it falls back to the existing heuristic (`path=heuristic`); the two paths are distinguishable via the response body and the persisted `model_id / model_version`; when ClickHouse is not configured, it degrades honestly to `available=false`.
- Training scheduling (Control-side automatic retrain and re-register): `MLModelService.scheduledMlRetrain()` (cron defaults to daily 04:20) delegates to `MlRetrainScheduler` — discover games with registered artifacts → spawn the `python3 -m oddsmaker_ml train --model all` subprocess (data source prefers real ClickHouse data: CH available and HTTP url derivable; an explicit `oddsmaker.ml.retrain.clickhouse-url` takes priority, otherwise derived from the JDBC url; when unavailable, falls back to synthetic data per the `allow-synthetic` switch to keep the run-through working) → validate and register artifacts one by one (same-version overwrite, hence idempotent) → trigger the four batch scoring write-backs to predictions. Period and switches are configurable (`oddsmaker.ml.retrain.*`, `enabled` off by default); training failures / invalid artifacts / scoring exceptions write audit entries (FAILURE / PARTIAL / SKIPPED, actor=`ml-retrain`) and degrade honestly without blocking existing pipelines, and a single game's failure does not block the others.

### Crash / Risk Reports and Segment Linkage (P7 wrap-up)
- Crash monitoring (top groups / trends / crash rate by version) and the risk dashboard (trends / rule hits / severity / disposition status) all support segment filtering; the numerator and denominator subqueries of the crash rate by version are filtered simultaneously, keeping the crash rate within the segment's scope.
- MMP attribution has completed its selection evaluation (AppsFlyer / Adjust / Airbridge, recommending a "scheduled cloud-storage export → ingestion job" approach), **conditionally approved**: it will not start until the precondition (raw data export permission from any one MMP) is met. See `docs/mmp-attribution-evaluation.md` for details.

## Breaking Changes

- **ClickHouse `retention_daily` table structure change**: a `subject_id` column is added and included in the sorting key (SummingMergeTree folds and sums by key, so the subject dimension must be in the key). Existing deployments must rebuild the table via migration; migration script: `schema/sql/clickhouse/migrations/2026-09-retention-daily-subject-id.sql` (one-time execution, not idempotent).
- **retention-job is strongly coupled to the table structure**: the old job (5-column INSERT) errors writing to the new high-dimensional table, and the new job (6-column INSERT) also errors against the old table — during the upgrade window, you must operate in the order given in the "Upgrade Notes".
- Each Control API report endpoint gains the optional parameter `segment_id`; when not passed, behavior is identical to the old version, with no compatibility impact.

## Upgrade Notes

1. **Run DB migrations**: `V0.9.12__segments.sql`, `V0.9.13__dashboards.sql`, `V0.9.14__dimension_sync_status.sql`, `V0.9.15__ml_model_artifacts.sql` (applied automatically by Flyway).
2. **Apply ClickHouse changes**:
   - New deployments: import `schema/sql/clickhouse/analytics.sql` and `segments.sql` directly to get the new structure;
   - Existing deployments: first stop the old retention-job → execute `migrations/2026-09-retention-daily-subject-id.sql` (historical rows keep an empty-string `subject_id`, non-segment retention semantics unaffected) → deploy the new retention-job.
3. **Flink jobs**: retention-job must be upgraded to the image bundled with this version (with subject_id output); the other jobs are unchanged.
4. **Permissions**: if using RBAC, grant `segment:read / segment:manage / dashboard:read / dashboard:manage / dimension:read / dimension:manage / ml:read / ml:manage` to the roles that need them (`export:execute` is an existing permission).
5. **Export directory**: confirm the control-plane export directory is writable and the ops sync task (object-storage side) is in place before opening the export page to analysts.
6. **Training pipeline (optional)**: to use the `ml/` training pipeline, prepare Python ≥3.10 and `pip install numpy pandas scikit-learn`; for automatic retrain scheduling, configure `oddsmaker.ml.retrain.*` (`enabled=true`, cron, python-bin, ml-dir, timeout-seconds, allow-synthetic, etc., all off by default); if unused, there is no impact whatsoever (Java/frontend do not depend on a Python runtime).

## Known Gaps

- Segment report semantics: each report's filter key matches the segment member subject key (player>user>device as primary; risk reports are user-first); when subject keys mismatch, that report returning an empty set is the expected semantics.
- The Live Inspector ring buffer is in-memory state of the Gateway process; it is cleared on restart and is intended only for real-time integration troubleshooting, not as a replacement for event auditing.
- Raw data export uses a directory-landing mode with a 5-million-row cap per partition; larger scales require ops-side sharding.
- The segment retention real-time fallback path clamps the window to 90 days; segment retention for earlier cohorts must wait for pre-aggregated data to accumulate.
- A PATTERN sequence rule tracks only one in-progress sequence per subject at a time (when a new sequence's first step appears, it restarts from the newest one); cross-sequence parallel combinations are out of scope for this version.
- The dimension sync agent covers five source types: mysql / postgres / csv / excel / kafka; kafka has been verified end-to-end against apache/kafka:3.7.0 (single node: all five green — earliest startup / checkpoint-seek resume / mid-run partition expansion / poison-pill skip with offset advancement / drain cap; SASL_PLAINTEXT+SCRAM-SHA-256 auth loop and failure on wrong credentials verified; 3-node KRaft multi-address bootstrap tolerating a dead address, stopping one broker with 2/3 alive all green — note that 2-node KRaft has no single-node tolerance, voters quorum = 2/2, losing any one node loses the controller quorum; 200k messages drained at 16k msg/s with zero loss, `-Xmx256m` peak heap 139MB). Unreachable-environment cases always auto-SKIP to avoid false failures. TLS(SSL) certificate chains have been tested (`KafkaSourceSslBrokerE2ETest`, three arms: self-signed CA single-node SSL + SASL_SSL dual listener): the client truststore's three keys `source.kafka.ssl-truststore-path/-password/-type` injected into a full consume loop + checkpoint resume with correct offsets (configuring a truststore under a plaintext protocol fails fast at startup); an untrusted chain was tested to throw `SslAuthenticationException` synchronously (cause chain PKIX path building failed), not a silent degradation; the SASL_SSL combined arm (SCRAM stacked on the certificate chain, wrong credentials still deterministically observable). mTLS mutual authentication was also tested (a third listener on the same broker `MTLSHOST://:29099`, listener-level `ssl.client.auth=required`): the client keystore's three keys `source.kafka.ssl-keystore-path/-password/-type` are injected via `SslSettings`, and topic creation/production/consumption all go through the mutual-auth listener with checkpoint resume advancing offsets precisely; truststore-only without presenting a certificate was tested to be rejected after the final stage of the TLS1.3 handshake (`SslAuthenticationException("Failed to process post-handshake messages")` ← `SSLHandshakeException("(bad_certificate) …")`), distinguishable from the PKIX form of an untrusted chain. Certificate orchestration scripts at `agents/dimension-sync-agent/src/test/ssl/` (CA/broker/client certs and private keys land only in OUT_DIR, never in the repository). Not covered: long-run stability.
- Gateway Kafka publisher real-broker coverage (tested against apache/kafka:3.7.0 + Apicurio Registry 2.6.5.Final): DlqPublisher wire payload verified byte-for-byte, AvroPublisher auto-registering schemas over the full loop (AvroKafkaDeserializer read-back of fields), and registry unavailability throwing RestClientException synchronously on the calling thread. Testing surfaced two operational points: ① when the broker is unreachable, producer.send() blocks the calling thread for the full max.block.ms (default 60s) before returning, and the TimeoutException goes into the FutureFailure — the DLQ fire-and-forget ignores the future, so that DLQ message is silently lost with no log and no metric; ② Avro schema REQUIRED fields (such as device_id) are guaranteed by BatchController's upfront validation, and only the real serializer checks for null (mocks do not expose this) — a missing REQUIRED field throws an NPE at publish.
- The training pipeline's first release has only linear interpretable models (LR / through-origin WLS); GBDT accuracy upgrades, multi-snapshot out-of-time extrapolation validation, and real-time scoring will be added on demand; the automatic retrain scheduler's first release is single-process serial, with the training artifact version fixed (the `model-version` config) — multi-version canary switching will be added on demand.
