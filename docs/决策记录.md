# Decision Log

Ledger of "delegated decisions" in this repo: patrol-round decisions made without an explicit order-level
mandate are recorded here one by one; the user may overturn any of them at any time — when overturning,

## FW1016D (2026-10-16): how "ruleConditions references EventSchema fields" was landed

**Decision**: the legal value domain of a FEATURE rule's `ruleConditions.features[].feature` is the feature
registry registered on the risk-job compute side (the first 6 features of B5); unknown names are rejected
at write time. Cross-validation against EventSchema is **not** performed.

**Rationale**:
1. FEATURE conditions reference derived features of "signal × window" (`gold_gain_1h`,
   `account_count_per_ip`, …), not raw fields of the event contract (EventSchema) — cross-validating
   feature names against EventSchema is semantically unsound and would reject every legitimate
   feature rule.
2. A rule with an unknown feature name can never fire in production (the `risk_features` table has no
   such key; risk-job skips the whole rule when parsing every 60 seconds), so it used to be silently
   skipped — the same write-path discoverability gap already tightened for shape-level validation
   (scope/feature/op/value).
3. The feature-name list is produced by risk-job alone and is naturally enumerable; registering it as
   constants pinned by tests on both sides to the same documented list mirrors the existing signal
   registry (`RiskSignals` mirrored on both sides).

**Impact**:
- risk-job: adds the `RiskFeatures` source of truth; `RiskJob.buildFeatureBranch` and the `FeatureCalc`
  feature-class constructors now reference the constants (feature name values unchanged, no behavior
  change).
- control-service: adds the `service/RiskFeatures` mirror plus an unknown-name check in the FEATURE
  branch of `RiskRuleService.validateConditions` (error message contains `known feature`).
- Unchanged (compatibility-first hard rule): the `ruleConditions` JSON shape, the `rule_conditions`
  column, existing rows (the demo DB has 0 FEATURE rows — no legacy exposure), the read path
  (tolerant skip semantics of replay/RuleFetcher), and all existing metric names; the only change is
  the new write-path check.
- The two sides share no dependency module; changing the list must land on both sides in the same
  batch (each side's tests pin the same DOCUMENTED baseline).

**How to overturn**: delete `service/RiskFeatures` and the unknown-name check branch in
`validateConditions`; revert `RiskJob`/`FeatureCalc` to the string literals; remove both `RiskFeatures`
classes together with their tests, restoring shape-level validation only.

## FIRE1019 (2026-10-19): clickhouse-backup.sh rewritten to the real Altinity 2.8.x CLI contract

**Decision**: `deploy/backup/clickhouse-backup.sh` is rewritten against the empirically verified
clickhouse-backup 2.8.1 contract, and its `incremental` mode degrades to a full backup with an
explicit log line when no `S3_BUCKET` is configured.

**Rationale**:
1. The DR-001 ClickHouse drill ran the script for the first time since it entered the repo (real
   clickhouse/clickhouse-server:24.8 + real 2.8.1 binary). Every invocation surface was wrong:
   connection flags (`--host/--port/--user/--password`) do not exist as CLI flags in 2.8.x
   ("flag provided but not defined"), `create` has no `--diff-from` (incrementals only exist on the
   upload face), `upload` has no `--storage-class`, and `BACKUP_DIR` defaulted to a directory the
   tool never writes (local backups land under `<CH data dir>/backup/`, configurable nowhere) — so
   retention silently scanned an empty dir. Same family as the `wal_archive_timeout` GUC bug: a
   delivered artifact with zero real execution surface.
2. Connection now goes through the tool's own environment variables
   (`CLICKHOUSE_HOST/PORT/USERNAME/PASSWORD`); the script bridges `CLICKHOUSE_USER` →
   `CLICKHOUSE_USERNAME` because the 2.8.x config key is `username`, not `user`.
3. Incremental-without-remote fallback to full mirrors the repo's existing postgres CronJob posture
   (weekly job is just another full, "不再注入无接线效果的 BACKUP_TYPE") — a real local backup beats
   a failed job; the log line keeps the degradation visible instead of impersonating an incremental.
   With `S3_BUCKET` set, the incremental chain is real: `create` + `upload --diff-from=<last full>`.

**Impact**: one script rewritten; new `ClickhouseBackupCliContractTest` (8 tests, red→green) pins
the contract; `BackupScriptTest` sandbox gains `awk/sort/tail` (the `list local` pipeline needs
them). `backup-strategy.md` §ClickHouse/§Scenario 3 reconciled: `restore latest_full` proven
invalid on 2.8.x (FTL: no such metadata file) and replaced with `restore_remote <name>`; CH
scheduling noted as unwired. Drill evidence (full/incremental/restore chain 12000 rows with
post-backup batch excluded, dead-endpoint exit 2) recorded in the strategy doc §Testing.

**How to overturn**: revert the script rewrite and the doc blocks; delete
`ClickhouseBackupCliContractTest`; if a future clickhouse-backup version reintroduces CLI
connection flags, re-pin the contract test to that version's `--help` output first.

## FIRE1019E (2026-10-19): release automatic rollback — prev-image capture, ERR trap, sandbox-tested rollback script

**Decision**: `.github/workflows/release.yaml` now rolls back automatically. A new
`Record running images` step runs before rollout and captures both services' current images via
container-name-filtered jsonpath into `$GITHUB_ENV` (`prev_control` / `prev_gateway`); a missing
deployment (first-ever release) yields an empty value instead of failing the step (`|| true`).
Both `Deploy to production` and `Verify deployment` run `set -euo pipefail` and set
`trap 'bash deploy/k8s/rollback-release.sh "$prev_control" "$prev_gateway"' ERR`, so a failed
apply, a rollout timeout, a failed in-pod health check, or a failed running-version assertion all
roll both deployments back. `deploy/k8s/rollback-release.sh` sets each container back to its
previous image and waits for `rollout status`; it deliberately runs without `set -e` (one
service's failed rollback must not abort the other's), skips an empty prev image with a
`::warning::` (nothing to roll back to on the first release), and exits non-zero if any rollback
failed.

**Rationale**: closes the last in-repo DEPLOY-001 acceptance item —「回滚步骤经过验证」. Until
now a failed release only turned red: production stayed pinned to the freshly pushed, broken
image. Verification is mechanism-level: `ReleaseDeployContractTest` grew from 5 to 11 tests,
all red→green, including three sandbox runs of the script against a stub `kubectl` (PATH holds
only the stub bin, so the host's kubectl can never answer) that prove the empty-prev skip issues
no `set image` at all, that both services get `set image` + `rollout status` against the recorded
prev image, and that a failing `set image` for control still lets gateway roll back while the
script exits non-zero. Live-cluster rollback stays external — the release workflow has zero
execution history (`git tag` holds only `nightly`, no `v*`).

**Impact**: workflow + one new script + tests; no release triggered, no tag created.
`deploy/MODES.md` K8s row notes the rollback script; the audit tracker's DEPLOY-001 entry records
the rollback closure and its external remainder, and the OBS-001 evidence cell was refreshed to
post-secret-split line numbers (`gateway-service.yaml:50-52,124-126`). The workflow pin test now
also asserts the prev-image capture shape (per-container jsonpath, `$GITHUB_ENV`, first-release
tolerance) and counts exactly two ERR traps — Deploy and Verify.

**How to overturn**: if rollback on a verify-stage failure is judged too aggressive (a flapping
health check would bounce an otherwise good release), remove the trap from `Verify deployment`
only — the pin test expecting exactly two traps makes that removal visible. If the previous-version
source changes (e.g. an annotation- or GitOps-based record instead of `GITHUB_ENV`), replace the
capture step and the script's two-argument contract together.
